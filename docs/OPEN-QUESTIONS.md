# 未確定事項リスト（Open Questions）

実装に入る前に決めておきたい論点。優先度は以下の 3 段階。

- **P0**: 最初の PR（M0-1）をブロックする。今すぐ決めたい
- **P1**: v0.1 の途中までに決めたい。後から変えると手戻りが大きい
- **P2**: v0.3 以降で決めればよい

決まった項目は「決定」欄に記入し、根拠を `docs/adr/` に ADR として残す。

## B. 設計上の未確定（P0/P1 が中心）

| # | 優先 | 論点 | 詳細 | 暫定案 | 決定 |
|---|---|---|---|---|---|
| B1 | **P0** | **外部依存パッケージを許容するか** | `netstandard2.0` で `Span<T>` を使うには `System.Memory`、`ArrayPool` には `System.Buffers`、`HashCode` には `Microsoft.Bcl.HashCode` の参照が要る。**「依存ゼロ」を最優先するなら ns2.0 側は素の配列 + index だけで書く必要があり、コードが二重化する** | **依存ゼロを採る**（ZDD エンジンは元々素の配列で書くので `Span` の必要性が低い。`IArrayDdSpec` の `Span<int>` は ns2.0 では `int[] + offset` のオーバーロードにする） | |
| B2 | **P0** | **BDD も扱うか** | TdZdd は BDD/ZDD 両対応。BDD も持つとノード表を共有でき応用も広がるが、演算セットが倍になる | **ZDD 専用**。BDD が要るなら別ライブラリ | |
| B3 | **P0** | N 分岐（N-ary）DD を将来サポートするか | TdZdd は `N` をテンプレート引数に取る。C# でジェネリックにすると全域に波及する | **2 分岐固定**。多値変数は 1-hot 符号化で対応 | |
| B4 | **P1** | `Zdd` ハンドルの形 | (a) `struct Zdd { ZddManager Manager; int Id; }`（16 B、API が快適）/ (b) `struct ZddRef { int Id; }` + マネージャを明示的に渡す（4 B、高速だが冗長） | (a)。演算子オーバーロードが使えて誤用も防げる。マネージャ不一致は例外 | |
| B5 | **P1** | 変数の向きと公開方法 | 内部は TdZdd 互換で「レベル N = 根側、1 = 葉側」。ユーザには 0-based の `Item` を見せる | `Item i ↔ Level (N - i)`。列挙が自然な辞書順になる向きに合わせる | |
| B6 | **P1** | スレッド安全性の保証レベル | (a) `ZddManager` は完全に非スレッドセーフ / (b) 読み取り専用の並行アクセスは許す / (c) 完全スレッドセーフ | (a) を既定、v0.4 で構築器内部の並列化のみ対応。ドキュメントに明記 | |
| B7 | **P1** | 変数数を後から増やせるか | 固定 `ZddManager(n)` / 動的追加 | **固定**。動的追加は一意化表の再構築が必要で複雑 | |
| B8 | **P1** | `Complement()` の全体集合 | マネージャの全変数 2^N / `Support` のみ | **マネージャの全変数**。`ComplementWithin(items)` を別途用意 | |
| B9 | **P1** | 列挙時の配列アロケーション | (a) 毎回 `new int[]`（安全、GC 圧） / (b) バッファ使い回し（速いが LINQ で壊れる） | (a) を既定、`EnumerateInto(buffer)` として (b) も提供 | |
| B10 | **P1** | 重み型の扱い | `long` 固定 / `double` 固定 / ジェネリック `IWeightOps<T>` | ジェネリック（`long`/`double`/`BigInteger` の実装を同梱）。ns2.0 でも struct 制約で devirtualize される | |
| B11 | **P1** | 上限超過時の挙動 | 例外 / `TryBuild` で false / コールバックで中断 | `ZddResourceLimitException` を既定、`TryBuild` も提供、`CancellationToken` を構築 API に通す | |

| B15 | **P2** | 動的変数順序変更（sifting） | 実装する / しない | **しない**。ZDD ではフロンティア法の辺順序最適化のほうが遥かに効く | |

## D. スコープ・利用目的（**ここが最も回答がほしい**）

| # | 優先 | 質問 | なぜ聞くか |
|---|---|---|---|
| **D1** | **P0** | **実際に解きたい具体的な問題はあるか？**（経路列挙／ネットワーク信頼性／選挙区割り・地域分割／配電網構成／組合せ最適化／数え上げ研究／ゲーム AI など） | 実装するスペックの優先順位が変わる。「とりあえず全部」より、1 つの実問題を最短で解けるようにしたほうがライブラリの質が上がる |
| **D2** | **P0** | **想定グラフの規模**（頂点数・辺数の桁） | フロンティア幅の想定 → 状態表現・メモリ設計に直結。数百辺なら現設計で十分、数万辺なら別の工夫が要る |

| **D6** | P2 | DOT 以外の可視化（SVG/HTML のインタラクティブ表示）は要るか | 要るなら別パッケージを立てる |
| **D7** | P2 | 期限やリリース目標日はあるか | あればマイルストーンの取捨選択が変わる（M4 の性能改善は最も削りやすい） |

## E. 決定が要らない（このまま進める）事項

念のため明示しておく。異論があれば指摘してほしい。

- ノード ID は `int`（2^31 ノード上限、約 32 GB）。64bit 版は作らない
- 一意化表・状態表は自前のオープンアドレス法（`Dictionary` は使わない）
- 家族代数演算は**すべて反復実装**（再帰禁止）
- 演算キャッシュは lossy direct-mapped（衝突は上書き）
- 参照カウントは実装しない
- 参考 OSS のコードはコピーせず、論文・ドキュメントから再実装する
- テストは xUnit ＋ CsCheck（プロパティテスト）＋ 総当たり照合
