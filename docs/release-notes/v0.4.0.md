# v0.4.0 リリースノート（2026-09-03）

M4「性能と残りのスペック」マイルストーン（[docs/PLAN.md](../PLAN.md) §12）の完了リリース。
性能改善（キャッシュ調整・SIMD 化・並列構築）を実測付きで積み上げ、残っていたグラフ系スペック
（連結部分グラフ・シュタイナー木・分割・カット・彩色・オートマトン）で機能面が出揃った。
Graphillion・TdZdd との比較で [docs/PLAN.md](../PLAN.md) §10 の性能目標を全て達成し、v0.5（I/O・GC）
と v1.0（安定化・公開）へ進む前提が整った状態になる。

## ハイライト

- **性能改善が中心テーマ**。演算キャッシュのサイズ自動調整（拡大時に生きているエントリを移行、
  代表ケースで実行時間 15〜20% 改善）、状態ハッシュの SIMD 化（`Vector256`/`Vector128`、フロンティアが
  広いケースで 7〜17% 改善）、フロンティア構築の並列化（`BuildOptions.MaxDegreeOfParallelism`。
  組み込みスペックでは大きくは伸びないが `GetChild` 自体が重いスペックには実際に効く、
  4 コアで 2.44x）を実装。どの変更も**構築される ZDD のノード ID は変更前後で完全一致**する
- **Graphillion・TdZdd との比較**（`bench/comparison`）で `docs/PLAN.md` §10 の 3 つの性能目標
  ——9×9 格子 1 秒以内・11×11 格子 60 秒以内/メモリ 8 GB 以内・Graphillion 比 3 倍以内（最終的に
  2 倍以内）——を**全て達成**。測定した 8 ケース全てで Graphillion を上回った（0.017x〜0.75x）。
  一方 TdZdd（P/Invoke・GC を持たない生 C++）には全ケースで 2.0x〜21.4x 遅く、これは想定内の結果
  として正直に記録した（「C++ に勝つ」ではなく「同じオーダーで .NET から依存なしに使える」ことが
  価値、という docs/PLAN.md §0 の位置づけと整合）
- **残りのグラフ系スペック 6 つ**を追加: `ConnectedSubgraphSpec`（連結部分グラフ）・
  `SteinerTreeSpec`（シュタイナー木）・`GraphPartitionSpec`（k-way 区割り）・`CutSpec`
  （s–t カット）・`ColoringSpec`（k 彩色）・`DfaSpec`（決定性有限オートマトンの汎用スペック）。
  `SpanningTreeSpec` → `ConnectedSubgraphSpec` → `SteinerTreeSpec` の一貫性（terminal 2 個で
  `PathSpec` と一致、全頂点 terminal で `SpanningTreeSpec` と一致）をテストで確認済み
- `docs/frontier-guide.md` に新しい「性能チューニングの指針」節を新設: 辺順序戦略の選び方、
  `BuildOptions` の並列度、ServerGC/TieredPGO、`EstimateMaxFrontierSize()` による事前判断を
  1 箇所に集約
- API はプレリリース扱いで、v1.0 までは破壊的変更があり得る

## 既知の制約

- `BuildOptions.MaxDegreeOfParallelism` は、このライブラリの組み込みスペックでは状態表への登録
  コストが `GetChild` 自体より重いため、大きな高速化は見込めない（4 コアで 0.9x 前後）。
  `GetChild` 自体が重い独自スペックでは実際に効く（docs/benchmarks.md M4-3 節）
- Graphillion（C++ コア）との比較は Python バインディング経由（issue #51 の指定どおり）で、
  C++ コアを単離した比較ではない——ZDD.Net にとってはむしろ甘い比較になっている可能性がある
  （docs/benchmarks.md M4-8 節）
- TdZdd（生 C++・ヘッダオンリー）との定数倍差（特に格子パスで顕著、最大 21.4x）を縮める余地は、
  フロンティア状態表への書き込みコストのさらなる削減にある——次の版の検討事項
- `IHybridDdSpec<TScalar>`（スカラ + `int` 配列の複合状態）は契約のみで、
  `FrontierBuilder.Build` のオーバーロードは未対応
- API はプレリリース扱いで、v1.0 まで破壊的変更があり得る
